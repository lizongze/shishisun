# 任务卡片编写建议（事事顺版）

> 适用场景：在「事事顺」中录入投标任务、开发任务、团队协作事项时参考。
> 核心原则：**标题一眼看懂，笔记能直接开工，完成与否无争议。**

---

## 一、事事顺字段与卡片要素对照

| 要素     | 事事顺字段                | 填写要求                                                   |
| -------- | ------------------------- | ---------------------------------------------------------- |
| 标题     | 事项标题                  | 动词 + 对象 +（目标/范围），不写"处理一下"这类模糊词       |
| 描述     | 自由笔记（支持 Markdown） | 背景 + 验收标准 + 依赖，按模板写                           |
| 排期     | 开始 / 截止日期           | 截止日默认当周周五；跨周任务拆分                           |
| 优先级   | 高 / 中 / 低              | 高=阻塞他人或影响投标/交付；中=本周须完成；低=可延后       |
| 归属     | 项目 + 标签               | 项目（如：车联网项目、事事顺）+ 类型标签（如：投标、开发） |
| 负责人   | 指派成员                  | 一事一人为主；多人协作写主责，其余在笔记中注明分工         |
| 过程记录 | 跟进日志                  | 有进展/问题/决策就补一条，不改原笔记                       |

---

## 二、标题怎么写

**格式：动词 + 对象 +（目标/范围）**

| 反例     | 正例                                              |
| -------- | ------------------------------------------------- |
| 标书的事 | 完成 XX 银行智能体项目技术标书初稿                |
| 优化一下 | 优化登录界面验证码发送频率（1 分钟内限 1 条）     |
| 对接     | 对接 srdcloud 平台 10-15 份标书的报名与保证金缴纳 |

> 自查：团队里随便拉一个人，只看标题能否说出"这事是干什么、干到什么程度"。

---

## 三、自由笔记推荐模板（直接复制使用）

```markdown
## 背景 / 用户故事
作为（角色），我希望（做什么），以便（达成什么价值）。
一句话交代为什么做、谁受益。例：作为投标负责人，我希望提前
完成资质文件核验，以便开标当天不因材料问题被废标。

## 验收标准
- [ ] 条件一（可检查、可演示）
- [ ] 条件二
- [ ] 异常/边界情况的处理方式

## 依赖与风险
- 前置：依赖 XX 接口 / XX 人提供资料（截止 X 日前）
- 风险：如 XX 未确认，则 XX 兜底

## 技术备注 / 交付物
- 交付物：文档路径 / 代码分支 / 系统页面
```

## 四、验收标准写法

好的验收标准满足三条：**可测试、无歧义、有边界**。

| 坏写法       | 好写法                                                 |
| ------------ | ------------------------------------------------------ |
| 界面美观     | 关键页面通过 Chrome Lighthouse 无障碍评分 ≥ 90         |
| 数据准确     | 导出报表合计数与后台统计一致，误差为 0                 |
| 尽快完成     | 10-17（周五）前提交，含自测截图                        |
| 提升登录体验 | 支持短信验证码登录，60 秒内可收到，错误提示不超过 4 种 |

## 五、排期与优先级约定

- **"本周"= 截止日设在当周周五**，团队统一基准。
- 单张卡片工作量控制在 **1~2 人天**；超过就拆：
  - 一份完整投标任务可拆为：资质文件核验 → 技术方案编写 → 商务报价核算 → 标书封装上传。
  - 拆出的子任务各自有独立验收标准，能单独流转状态。
- 排期时先看依赖：被依赖的卡片排前面，优先级标高。
- 临时插入的任务：先快速判断"今天不做会不会阻塞别人"，是 → 高优排今天，否 → 按原计划。
- **长期任务（跨周/跨月）不适用"截止=当周周五"**，按真实硬节点排期，见第九节。

## 六、INVEST 自查清单（录入前 30 秒过一遍）

| 字母 | 含义   | 自查问题                                          |
| ---- | ------ | ------------------------------------------------- |
| I    | 独立   | 这张卡能否不依赖其他未完成卡片直接开工？          |
| N    | 可协商 | 实现细节是否留有讨论空间，没有写死？              |
| V    | 有价值 | 完成后对投标/产品/团队有可感知的收益吗？          |
| E    | 可估算 | 负责人能否大致说出要花多久？说不清 → 再拆或先调研 |
| S    | 小而精 | 1~2 天内能完成吗？超了 → 拆分                     |
| T    | 可测试 | 验收标准里的每一条都能被检查吗？                  |

**任一问答不上来，就先补笔记或拆卡片，再录入/流转。**

## 七、完整示例

```
标题：完成 XX 银行智能客服项目技术偏离表填写
项目：金融行业智能体（标签：投标）   负责人：陈美君
排期：10-13 ~ 10-16（周四）前完成初稿，预留周五复核
优先级：高（阻塞标书封装）

自由笔记：
## 背景 / 用户故事
作为投标负责人，我希望技术偏离表在封标前 1 天完成，
以便留出时间处理负面偏离的澄清说明，避免废标。

## 验收标准
- [ ] 招标文件技术要求逐条应答，无遗漏项
- [ ] 偏离项标注"正偏离/负偏离/无偏离"，负偏离附澄清说明
- [ ] 格式与招标文件第 X 章要求一致（表头、字体、份数）
- [ ] 经刘超复核签字确认

## 依赖与风险
- 前置：技术方案 v2（负责人：刘超，10-14 前提供）
- 风险：招标文件第 8.3 条要求不明确 → 10-14 前向招标代理电话确认

## 交付物
偏离表（Excel）上传至团队共享盘「XX银行标书」目录
```

**跟进日志用法**：10-13 已通读招标文件 38 条技术要求（陈美君）；10-14 第 8.3 条已与招标代理确认按满足响应，记录在案（陈美君）。

好的日志写"做了什么、结论是什么、下一步谁接手"，不写流水账。详细规则见第八节。

## 八、跟进日志怎么写

### 1. 什么时候写（触发时机）

不是每天都写流水账，出现以下情况才写一条：

- 完成一个阶段 / 交付了一个东西
- 遇到阻塞、风险、意外（含需要谁支援）
- 做了关键决策（尤其是影响后续判断的：与招标代理确认条款、变更技术方案等）
- 计划有变（排期调整、范围增减，顺带写明原因和谁拍板）
- 需要他人知晓或准备接手

> 反面："今天继续弄标书""推进中"这种没有信息量的日志，宁可不写。

### 2. 一条好日志的三段结构

**做了什么（事实）→ 结论是什么（判断）→ 下一步（谁、何时、干什么）**

| 坏日志（流水账） | 好日志                                                                                         |
| ---------------- | ---------------------------------------------------------------------------------------------- |
| 今天继续弄标书   | 技术偏离表 38 条已完成 30 条；剩余 8 条依赖技术方案 v2（刘超 10-15 提供）；预计 10-16 提交初稿 |
| 打电话问了       | 已与招标代理确认第 8.3 条按"满足"应答，无需澄清（通话记录存共享盘）；偏离表按无偏离填写        |
| 有问题，进展慢   | 商务报价模板与招标文件格式不符，已请示换新版（今日内回复）；不影响 10-17 封标                  |

要点：

- **写结论和数字**："完成 30/38 条""误差为 0""10-16 可交初稿"，让别人看完日志不用再来问你情况
- 补记时把日志日期改成实际发生日，别把时间线弄乱
- 一条日志只写一件事；同一天多件事就写多条，方便日后检索

### 3. 日志与笔记的分工（最易混淆）

|            | 自由笔记                                                   | 跟进日志                                  |
| ---------- | ---------------------------------------------------------- | ----------------------------------------- |
| 定位       | **当前状态**：任务是什么、验收标准、依赖清单               | **时间线**：过程、决策、进展，按时间沉淀  |
| 什么时候动 | 结论性信息变化时才改（依赖解除、验收标准更新、里程碑状态） | 有触发时机就追加一条                      |
| 举例       | "前置：技术方案 v2 已于 10-15 提供"                        | "10-14 向招标代理确认 8.3 条，按满足应答" |

简单判断：这条信息**"以后只需要最新版"→ 改笔记；"需要知道何时发生的"→ 写日志**。

### 4. 交接场景检验

换人接手时，接手人只看笔记 + 从下往上翻日志，就应能掌握全貌。所以关键日志要写到"外人也看得懂"——少用只有团队内部明白的代称，人名、文件名、日期写全。

## 九、长期任务怎么写（跨周 / 跨月）

### 1. 什么算长期任务

- **有终点但跨度大**：如"XX 银行智能体项目投标"（从报名到开标 3~6 周）、产品迭代、跨月开发——预计超过 2 周无法关闭
- **持续型/无终点**：如"金融行业智能体商机每日盯标"、系统运营值守

核心矛盾：**看板要流转，但事情本身不会很快完成**。解法：父卡挂总目标，里程碑拆子卡。

### 2. 父卡 + 子卡模式（事事顺没有原生父子关系，用约定关联）

**父卡——长期挂在看板上，状态反映大流程阶段（商机 → 投标 → 归档）：**

- 标题写最终交付物 + 硬节点：`XX 银行智能体项目投标（开标 11-20）`
- 排期：start = 启动日，due = 最终硬节点（开标日 / 交付日），**写真实节点，不受"当周周五"约束**
- 优先级：常态"中"，临近硬节点前一周升"高"；负责人 = 总协调人（如项目主责）
- 笔记放目标 + 里程碑表 + 关键外部依赖：

```markdown
## 目标
中标 XX 银行智能客服项目（预算 XXX 万，开标 11-20）

## 里程碑
| 里程碑 | 计划完成 | 状态 |
|--------|---------|------|
| M1 报名 + 资质文件核验 | 10-16 | 进行中 |
| M2 技术方案定稿 | 10-30 | 未开始 |
| M3 商务报价核算 | 11-06 | 未开始 |
| M4 标书封装上传 | 11-17 | 未开始 |
| M5 开标 | 11-20 | — |

## 关键外部依赖（不可错过）
- 招标文件澄清截止 10-23
- 保证金到账截止 11-10
```

**子卡——每个里程碑拆成独立的标准短卡片：**

- 标题带编号呼应父卡：`【XX银行投标-M1】资质文件核验`，同时用同一项目 + 标签聚合，看板里自然成组
- 每张子卡按第二~四节标准写：独立验收标准、1~2 人天粒度、截止按当周节点
- 子卡负责人写实际执行人（父卡负责人负责协调，不必亲自做子卡）

### 3. 维持长期任务不失焦的三个动作

1. **每周五更新父卡**：改里程碑表状态 + 写一条周报式日志（本周完成 / 下周计划 / 风险），与团队周五节奏对齐
2. **两周零变化的父卡视为风险**：既没改状态也没写日志 → 例会拿出来复盘：是忘了记，还是真的卡住了
3. **里程碑变化即时改父卡笔记**，日期调整写进日志（记原因和谁批准），别让父卡的表格过期

### 4. 持续型任务（无终点）的写法

- 不设 due（事事顺支持持续事项），验收标准转为**运转标准**：
  - 例："工作日每天 17:00 前完成 srdcloud + 3 个第三方平台扫描；发现高价值智能体标讯，30 分钟内建卡并通知负责人"
- 日志按天/按次记录结果："10-13 扫描 4 个平台，新增 XX 券商智能客服标讯 1 条，已建卡（负责人：陈美君）"
- 每月底写一条小结日志，统计扫描量、出卡量、转化跟进的商机数，把持续型任务的价值显性化；无产出连续一个月，就该评估是否停掉或改频次

## 十、常见问题速查

| 问题                 | 后果                   | 对策                                    |
| -------------------- | ---------------------- | --------------------------------------- |
| 只有标题没笔记       | 做完各执一词           | 笔记模板里验收标准必填                  |
| 一张卡塞一整块功能   | 流转不动，看板失真     | 超 2 人天必须拆分                       |
| 技术术语当标题       | 非技术人员看不懂       | 标题写业务语言，技术细节放笔记          |
| 进展靠口头同步       | 换人接手两眼一抹黑     | 阶段性结论写跟进日志                    |
| 日志写成流水账       | 关键信息埋没，检索不到 | 三段结构：事实 → 结论 → 下一步          |
| 长期任务一张卡挂到底 | 看不出进度、预警失效   | 父卡挂总目标 + 里程碑拆子卡，每周五更新 |
| 持续型任务永无终点   | 变成僵尸卡，没人看     | 验收标准改运转标准，每月写小结日志      |
| 截止日随手填         | 预警形同虚设           | 统一按"本周=周五"基准，跨周写真实节点   |
